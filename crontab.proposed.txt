# crontab.proposed.txt — DEADLINE-ALIGNED sweeps (replaces the whole crontab).
# DO NOT install by hand-editing crontab -e line by line; review, then:  crontab crontab.proposed.txt
# (Installation is the LEAD's call after verification — W1 only proposes.)
#
# Model: cron fires tools/cron/deadline_sweep.sh <slot> EARLY (2h lead window).
# The script predicts the serial chain's runtime from history (predict_lead.py),
# sleeps until <slot> - predicted_lead, runs ./run_all.sh with DEFER_DELIVERY=1,
# and send_batch.py holds every platform's report and delivers them as ONE batch
# AT the slot time ("everyone comes at the timing, not starts at it"). If the
# chain overruns, the batch goes out as soon as it's done, marked "(late by Xm)".
#
# NOTE (honest caveat from the bootstrap data): the two serial sweeps recorded on
# 2026-06-05 took ~3h05m platform-to-platform ( heal-retries + blinkit's
# patient re-resolution dominate). predict_lead clamps the lead to LEAD_MAX-120
# (=7080s ≈ 1h58m), so until the chain tightens, batches will start at the fire
# time and may land marked late. To guarantee on-time batches either fire earlier
# with a bigger window (e.g. 06:45/11:45 + LEAD_MAX=11700) or trim the chain.

# 10:00 IST slot — fire 08:00, sweep starts at 10:00 - predicted lead, batch lands AT 10:00.
0 8 * * * cd /opt/ecom-intel && LEAD_MAX=7200 ./tools/cron/deadline_sweep.sh 10:00 >> logs/cron.log 2>&1   # ecom-intel deadline-batch 10:00

# 15:00 IST slot — fire 13:00, same mechanics, batch lands AT 15:00.
0 13 * * * cd /opt/ecom-intel && LEAD_MAX=7200 ./tools/cron/deadline_sweep.sh 15:00 >> logs/cron.log 2>&1   # ecom-intel deadline-batch 15:00

# 18:00 IST daily guardian deep-dive — UNCHANGED from the live crontab (read-only
# 11-bug-class audit + trend; Telegram-alerts only on a NEW bug class vs yesterday).
0 18 * * * cd /opt/ecom-intel && ./tools/guardian_daily.sh >> logs/guardian.log 2>&1   # ecom-intel guardian-daily (paused w/ sweeps; un-pause together)
