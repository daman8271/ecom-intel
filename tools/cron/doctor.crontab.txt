# doctor.crontab.txt — ecom-intel cron block: deadline sweep + guardian + doctor + mailer
# plus the self-healing noon sweep watchdog and post-batch layout gate.
#
# This is NOT the whole root crontab on shared hosts. Merge these ecom-intel lines
# into the live crontab while preserving other repo schedules (jivo-intel, data-bank,
# competitor warroom, pincode app, push-all, Hermes, etc.).
#
# Cron runs in system-local time = IST (the live `0 18` guardian is 18:00 IST — confirmed).
#
# ============================ LIVE SWEEPS + GUARDIAN (UNCHANGED) ============================
# Model: cron fires tools/cron/deadline_sweep.sh <slot> EARLY. The live box now
# fires the 10:00 slot at 00:30 with LEAD_MAX=11820, and a watchdog polls every
# 20 minutes from 00:00-09:00 to catch a missed launch tick. The script predicts the serial chain's
# runtime from history (predict_lead.py), sleeps until <slot> - predicted_lead,
# runs ./run_all.sh with DEFER_DELIVERY=1, and send_batch.py holds every
# platform's report and delivers them as ONE batch AT the slot time ("everyone
# comes at the timing, not starts at it"). If the chain overruns, the batch goes
# out as soon as it's done, marked "(late by Xm)".

# Blinkit is produced off-box on the Mac Pro/residential IP and delivered through
# platforms/blinkit/ingest.sh. BigBasket pincode is produced by the logged-in
# team runner across VPS + Mac Pro + KVM1; it writes only to output/private-no-group
# and direct-sends from a gitignored direct-recipient secret. The old BigBasket
# paid QuickCommerce API cron is retired.
0 3 * * * cd /opt/ecom-intel && /usr/bin/tmux new-session -d -s "bbteam-$(date +\%Y\%m\%d)" 'flock -n logs/.bigbasket-team.lock ./platforms/bigbasket/team_run_pincode.sh run >> logs/bigbasket-team-pincode.log 2>&1'   # ecom-intel bigbasket-pincode team daily private-direct

# 10:00 IST slot — the ONLY sweep (owner cut 2x/day -> 1x/day 2026-06-28; moved
# 12:00 -> 10:00 goal #60 2026-07-03). Fire 00:30; LEAD_MAX=11820 is the current
# phase-2 live value. The watchdog guards the single 00:30 cron launch tick and only
# launches a bounded catch-up if the primary did not start.
30 0 * * * cd /opt/ecom-intel && LEAD_MAX=11820 COVERAGE_DAILY=1 ./tools/cron/deadline_sweep.sh 10:00 >> logs/cron.log 2>&1   # ecom-intel deadline-batch 10:00
*/20 0-9 * * * cd /opt/ecom-intel && ./tools/cron/sweep_watchdog.sh 10:00 >> logs/sweep_watchdog.cron.log 2>&1   # 10:00-sweep catch-up watchdog (guards the single 00:30 launch tick)
0 5 * * * cd /opt/ecom-intel && ./tools/cron/start_blinkit_live_watch.sh >> logs/blinkit_live_watch.cron.log 2>&1   # blinkit live watcher starter early
5 5 * * * cd /opt/ecom-intel && ./tools/cron/start_blinkit_supervisor.sh >> logs/blinkit_supervisor.cron.log 2>&1   # blinkit active supervisor starter
25 6 * * * cd /opt/ecom-intel && ./tools/cron/start_blinkit_live_watch.sh >> logs/blinkit_live_watch.cron.log 2>&1   # blinkit live watcher starter
35 6 * * * cd /opt/ecom-intel && ./tools/cron/blinkit_batch_guard.sh early >> logs/blinkit_guard.log 2>&1   # blinkit 10:00-batch guard early
45 8 * * * cd /opt/ecom-intel && ./tools/cron/blinkit_batch_guard.sh late >> logs/blinkit_guard.log 2>&1   # blinkit 10:00-batch guard late
*/15 5-10 * * * cd /opt/ecom-intel && ./tools/cron/blinkit_quality_monitor.sh poll >> logs/blinkit_quality_monitor.cron.log 2>&1   # blinkit quality monitor false-OOS guard

*/15 6-12 * * * cd /opt/ecom-intel && ./tools/whatsapp/send_blinkit_not_listed_direct.sh cron >> logs/blinkit-not-listed-wa.log 2>&1   # blinkit not-listed direct WhatsApp retry

# 18:00 IST daily guardian deep-dive — UNCHANGED from the live crontab (read-only
# 11-bug-class audit + trend; Telegram-alerts only on a NEW bug class vs yesterday).
0 18 * * * cd /opt/ecom-intel && ./tools/guardian_daily.sh >> logs/guardian.log 2>&1   # ecom-intel guardian-daily (paused w/ sweeps; un-pause together)

# ================================ ECOM DOCTOR (ADDITIVE) ====================================
# Self-healing watchdog. After the daily noon sweep has landed (12:00) and the 18:00
# guardian deep-dive has run, the doctor gathers deterministic health signals
# (tools/cron/health_snapshot.py) and — ONLY if something is wrong — invokes a bounded headless
# Claude agent (tools/cron/doctor_prompt.md + the vetted tools/cron/safe_fixes/ menu) to
# diagnose, auto-apply a VETTED-SAFE fix or PROPOSE-only, and ALWAYS alert the owner. It never
# pushes, only runs when ECOM_DOCTOR_ENABLE=1 (kill switch = unset it in secrets.env), and is
# flock-guarded so two doctors never overlap. A doctor crash can NEVER touch the sweeps above.
#
# WHY 18:30 daily: it must see the WHOLE day — the noon sweep batch (12:00 + its post-batch tail)
# AND the 18:00 guardian's fresh health-<date>.md. 18:30 is the first slot strictly
# after the guardian finishes (guardian is read-only/seconds), so the doctor reads the complete,
# settled signal set. The headline signal it exists to catch — a platform HELD N sweeps in a row
# (the 2-day silent flipkart/zepto false-positive hold) — is now visible once the
# day's sweep is in reviews/.
30 18 * * * cd /opt/ecom-intel && ./tools/cron/doctor.sh daily >> logs/doctor.log 2>&1   # ecom-intel doctor-daily

# WHY Sunday 19:00 weekly: a 7-day trend pass (held-platform frequency, recurring SUSPECT
# reasons, prediction-vs-actual drift, coverage trends) — runs after Sunday's daily doctor
# (18:30) so it never races it; 30m apart, both are short unless the agent is invoked (lock
# serializes that anyway).
0 19 * * 0 cd /opt/ecom-intel && ./tools/cron/doctor.sh weekly >> logs/doctor.log 2>&1   # ecom-intel doctor-weekly

# WHY 1st 19:30 monthly: a 30-day rollup — runs after the daily (18:30) and (when the 1st is a
# Sunday) after the weekly (19:00), each 30m apart and lock-serialized so they never overlap.
30 19 1 * * cd /opt/ecom-intel && ./tools/cron/doctor.sh monthly >> logs/doctor.log 2>&1   # ecom-intel doctor-monthly

# ===========================================================================================
# OVERLAP / SAFETY NOTES (doctor lines)
# - The three doctor lines are mutually exclusive in practice (18:30 / 19:00 / 19:30, ≥30m
#   apart) and additionally serialized by logs/.doctor.lock (flock -n in doctor.sh) — a long
#   agent run from the daily can never be clobbered by the weekly/monthly; the later one logs
#   "another doctor holds the lock" and exits.
# - All three run in the EVENING (18:30–19:30), well clear of the single sweep chain
#   (~05:51–12:00) and the 18:00 guardian (read-only, seconds). No
#   sweep/guardian overlap by construction.
# - The doctor reads artifacts only and (when it acts) calls vetted safe_fixes/ scripts that are
#   themselves lock-guarded (sweep-chain / amazon-account / .heal-<p>) and refuse during a live
#   sweep window — so even a safe-fix re-run can't collide with a sweep.
# - doctor.sh is fully fail-safe: if ECOM_DOCTOR_ENABLE!=1 it no-ops; any internal error still
#   fires an owner alert and exits 0; it has no path that can abort or modify the sweep crons.
#
# Scope: ecom-intel cron lines only. The live root crontab also contains other repo schedules.
# ===========================================================================================
10 10 * * * cd /opt/ecom-intel && python3 tools/cron/check_layout.py >> logs/layout_gate.log 2>&1   # ecom-intel layout gate (post 10:00 batch)

# ============================== PRICE-DATA MAILER (ADDITIVE) ===============================
# Emails the day's 9 report files AS-IS (each .xlsx an individual attachment, unmodified) to
# the 13-address ecom team list in mail_price_data.sh (override: PRICE_MAIL_TO in secrets.env)
# via Gmail SMTP (tools/send_email.py), then posts the same files to the WhatsApp
# "Ecom team" group via the Hermes gateway bridge (127.0.0.1:3001/send-media,
# owner-approved 2026-06-11; best-effort).
# Each run opens its own tmux session (mailgw-am/pm-YYYYMMDD) so the send gateway is
# observable live; it exits when done. Log: logs/mailer.log. The 10:00 run WAITS (up to 3h)
# until ALL of today's files exist and are >=90s stable — the single batch lands ~12:00 — so it
# never mails a partial/stale set. (The 16:00 pm run was dropped with the 15:00 sweep 2026-06-28.)
# Telegram-alerts the owner on any failure. Built 2026-06-11.
0 10 * * * cd /opt/ecom-intel && /usr/bin/tmux new-session -d -s "mailgw-am-$(date +\%Y\%m\%d)" './tools/mailer/mail_price_data.sh am'   # ecom-mailer price-data am
